# 每日复盘素材 → 成品复盘（按需触发）

> v1.4.6 起**不再有定时任务**：素材由用户**手动投递**（直接在对话里发截图 / 发文档，
> 或说「总结一下我们刚才聊的」），由本 SOP 生成当日复盘。原先的「晨间收集自动化」已删除，
> 本 skill 就是它的替代品 —— 但机制从 **always-on 调度** 换成 **按需加载**。
> 项目口径（评分 / 熔断 / 权威归属 / 规约）见 skill `dailylumen-conventions`，这里只讲流程。
> 总管家「夜间复盘」段挂本 skill：先 `steward --slot evening` 看清单，再按本文落地
> （见 skill `life-steward-daily`）。

## 0. 执行节奏（2026-10-15 定版 · 先读这一节）

**复盘是「次日晨间回顾昨日」，不是「当晚写当天」。**

| 项 | 口径 |
| --- | --- |
| 执行时点 | **次日早上**（起床后 / 通勤前；ClickUp「每日复盘总结」即在 08:4x 完成） |
| 产出对象 | **前一天** —— 10-16 早上生成的是 **10-15** 的复盘 |
| 文件名 | 用**被复盘那天的日期**：`每日复盘/复盘/2026-10/2026-10-15.md` |
| 数据块 `日期 / 星期` | 同上，写**被复盘的那一天** |

**为什么定成次日**：① 睡眠（入睡时刻 / 时长 / 质量）与屏幕总时长当晚拿不到闭环值；
② 用户实际习惯是「**当天做完、次日早上一起在 ClickUp 勾**」——与 v1.12.0「次日早上补勾」
回拨是同一个行为模式。

⛔ **别把「次日生成」当成日期写错**：这是**刻意的时点设计**。md 文件名与数据块日期
**一律是被复盘的那一天**，不是执行当天。

## 触发与开场

用户发来截图 / 文档 / 文字简报，或直接说「把今天复盘弄一下」时：

1. 先确认**归属日期**（见 §2），不确定就问一句。
2. 读取素材并抽取客观数据。
3. 按 §3 生成 / 更新复盘文件，按 §4 出「AI 评价与建议」。
4. 按 §5 收尾回复。

**开场白（可直接用）**：请把今日简报文字 / 相关截图直接发我；我抽取客观数据、
回填当日复盘并生成带「AI 评价与建议」的成品，输出到 `每日复盘/复盘/YYYY-MM/`。

## 1. 素材来源（本项目不再有收件箱依赖）

- **对话直发**（主路径）：截图（睡眠 / 运动 / 饮食 / 屏幕使用时间…）+ 文字简报
- **对话里发文档**：md / txt / pdf
- `每日复盘/收件箱/`：仍可用作**手动**投放点（素材多、跨设备时方便），
  但**不再有自动化去扫**，需要用户明确说「去收件箱读」才读
- **ClickUp 行为记录**（行为侧证据）：**一条命令拿到素材** ——
  `python -m review_tool clickup <YYYY-MM-DD>` → 落 `收件箱/clickup-素材-<日期>.md`
  （`--stdout` 只看不落文件）。它按 `date_closed`（东八区）归日（**含 v1.12.0「次日早上补勾」回拨**：当天做、
  次日早上才勾的归回 `due_date` 那天，素材里标「次日补勾」）、只读、**不参与评分**。
  空间结构与 list ID、映射口径、**两套打卡体系不许混**的边界见 skill **`clickup-tracking`**。
  ⚠️ ClickUp「习惯与打卡」的勾选**不进** md 的「一、日常打卡」—— 那一节只收补剂 / 护肤
  （`config.PERSONAL_ITEMS`），混进去会污染 `personal_tracks` 的依从率。
  ⚠️ 素材里若有「疑似批量改状态」提示（同一分钟 ≥10 条完成），**别**当成本人当天做了那么多事。
- 约束：**不删除、不改动**用户的原始素材；收件箱文件处理完保留
- ⚠️ **语雀（Yuque）粘贴会丢两样东西**（2026-10-02 实测）：
  1. **复选框状态** —— 渲染视图复制出来，`- [x]` / `- [ ]` 全变成纯文本
     「补剂：CoQ10 ×1 ＋ Exia 早3」，**看不出勾没勾**；
  2. **整段可能没选上** —— 本次「**晨间（起床后）**」那一整套（补剂 / 早餐 / 护肤）
     在粘贴里直接缺失，正文从「午间（午餐后）」开始。
  判据：**只要粘贴里看不到 `[x]` / `[ ]` 标记，就不要猜打卡**，用 `AskUserQuestion`
  一次问清「这天实际做了哪些（晨间 / 午间 / 晚间）」。打卡虽不进四维分，但会写进
  `personal_tracks` 污染依从率 —— 猜错就是假数据。段缺失时同理，别默认全做了。

## 2. 日期归属（最容易出错的环节）

按「**晨间回顾昨日**」惯例，数据归入其**真正代表的那一天**：

| 素材 | 归属 |
| --- | --- |
| 睡眠截图 | 归**入睡那一夜**（早上看到的睡眠报告 = 昨晚） |
| 饮食 / 屏幕使用时间截图 | 按图上标注的日期 |
| 运动截图 | 按图上日期；若为「今天刚做完」，归属当天 |
| 文字简报 | 按用户叙述的日期；跨天就分开处理 |

同一批素材可能跨两天 → **拆成两份复盘**，别硬塞进一天。

## 3. 生成 / 更新复盘文件

1. 在 `每日复盘/复盘/{YYYY-MM}/YYYY-MM-DD.md` 生成或更新（目录路径由 `config.py`
   的 `__file__` 推导，**不要写绝对路径**）。
   - **新的一天（默认流程）**：复制 `每日复盘模板.md` 到该目录、改名为当天日期，
     再把标题与数据块里的「日期」「星期」**两处**改成当天 —— 只有这两处需要改。
   - `python -m review_tool new-day` 能做同一件事，但**默认关闭**
     （`config.FEATURES['new_day'] = False`）：别依赖它，也别去打开它。
     真跑了它会打印手动路径并以退出码 2 结束，**不会写任何文件** ——
     看到那个提示就照提示手动复制，不要以为模板已经起好了。
2. 把客观数据回填进文末 **附录 · 系统数据** 的 ```` ```data ```` 块，字段顺序固定：
   日期 / 星期 / 训练日 / 睡眠时长_h / 睡眠质量 / 入睡时间 / 运动时长_min / 饮食热量_kcal /
   碳水_g / 脂肪_g / 蛋白质_g / 三餐情况 / 早餐按时 / 手机屏幕_h / 深度工作_h / 学习投入_h /
   生活投入_h / 一句话总结 / **体重_kg / 体脂率 / 腰围_cm**。
   - 缺数据**留空**，不要写「⚠️ 缺数据」之类的占位符
   - **不写「补剂完成」**（补剂 / 护肤由「一、日常打卡」勾选提取到 `personal_tracks`）
   - **不写 BMI**（派生值，由身高配置 + 体重在报告里算）
   - 不要塞图片注解、不要写截图路径
3. **用户原文照录**：一~五章节的叙述**原样保留、不改写**（AI 只补数据与评价）。
4. 入库算分：`python -m review_tool ingest`（⚠️ **只吃第一个路径参数**，多传静默丢弃；
   一次处理多天就循环调用。**传绝对路径** —— 相对路径会把 `raw_path` 改写成相对值，
   而 doctor 在项目根执行 `os.path.exists` 照样通过、不报错）
5. 回填六段：`python -m review_tool sync-docs`（**分数由库渲染，别在 md 里手改分数**）。
6. ⚠️ **补完「七、AI 评价与建议」和「一句话总结」之后，必须再跑一次 `ingest`。**
   `summary` 只在 ingest 时写库，`sync-docs` 完全不碰它 —— 而 §4 的 ingest 跑在写评价
   之前，所以漏这步的话 `daily_reviews.summary` 会整段留空（10-02~10-09 八天就中过）。
   **全程没有任何报错**：md 看着正常、`sync-docs --check` 仍是 0 篇、doctor 照样「数据健康」。

### 3.5 体征截图回填规则

体脂秤 / 体重秤截图是**输入通道**，不是数据源（G1）。流程：

1. 从截图读出数值 → 写入当日 md 数据块末尾三行：`体重_kg` / `体脂率` / `腰围_cm`
2. `python -m review_tool ingest` → 侧车落到 `body_metrics`（**不写** `daily_reviews`）
3. 查看趋势：`python -m review_tool body`（或 `--json`）

口径要点：

| 项 | 规则 |
| --- | --- |
| 归属日 | 按秤上标注的称量日；晨起称重归**称量当天** |
| BMI | **不写入 md**、不进库；身高在 `config.PROFILE["height_cm"]` |
| 来源 | 默认 `manual`；若明确来自体脂秤截图可在数据块加 `体征来源: scale` |
| 与四维 | **零关系** —— 独立指标区，不影响健康分 / 熔断 |
| 缺项 | 三行都可留空；有体重无体脂也合法 |

⛔ 禁止「只进库不落 md」—— 否则破掉「删库可从 md 100% 重建」。

### 3.6 饮食 / 薄荷截图回填（M12）

薄荷健康截图同样是**输入通道**。流程：

1. 读出热量 + 三大营养素 + 三餐/早餐按时 → 写入数据块
   `饮食热量_kcal` / `碳水_g` / `脂肪_g` / `蛋白质_g` / `三餐情况` / `早餐按时`
2. `ingest` 入库（**不**建食物明细表；日汇总即可）
3. 缺口与具体动作：`python -m review_tool nutrition`（数字来自 `FOOD_LIB`，可复算）

口径：缺口判定与 `ai-context` 关注点**同源**（`core/nutrition.py`）；连续 3 天 < 1000 kcal
会强提示，评价里**不要**把「吃得少」算做得好。不做医疗/营养处方。

### 3.6 训练截图 / 明细回填规则

练练 App / API / 自记训练截图是**输入通道**，不是数据源（G1）。

**优先（v1.22.0 / M20 起一并写训练日）**：
`python -m review_tool keepstrong --date YYYY-MM-DD --write --ingest`
（默认 dry-run；`--write` 幂等写入 keepstrong 标记块 + 数据块 `训练日: 是/否`，再 ingest）。
只取练练 `status=="completed"`；有 completed → `是`，成功拉到空 → `否`；
API 失败**不写「否」**（CLI 明示离线兜底，留给 `fill_training_day`）。
无 API 记录时不造空训练明细章节。对象日 = **被复盘日**（执行日的昨日）。
`steward --slot evening` 的训练步就是这条命令，`--date` = 该次复盘的归属日。

截图补录流程：

1. 从截图读出课名 / 动作 / 组次 → 写入当日 md **「附录 · 训练明细」**（在「附录 · 系统数据」之前）：

```markdown
## 附录 · 训练明细

- 计划：A-胸背｜来源：练练
- 俯卧撑 4×20
- 卧推 3×12 @40kg
- 平板支撑 3×60s
- 跑步 20min
```

2. `python -m review_tool ingest` → 落到 `training_sessions` / `training_items`
3. 查看建议：`python -m review_tool coach`（或 `--json`）

口径要点：

| 项 | 规则 |
| --- | --- |
| 行格式 | `组×次` / `组×次 @负重` / `Nmin` / `组×时长s` / 首行计划元信息 |
| `运动时长_min` | **字段优先**；仅当字段为空时由明细合计派生，标 `derived`（R2） |
| 与四维 | 明细**不直接**改评分；只经既有 `exercise_min` 路径 |
| 来源 | `练练` → `lianlian`；手填 → `self` |

⛔ 禁止「只进库不落 md」。有计时器读数时优先填数据块 `运动时长_min`，明细作证据。


### 3.7 学习记录回填规则

学习主题 / 产出是**输入通道**，权威仍是 md（G1）。流程：

1. 写入当日 md **「附录 · 学习记录」**（建议在「附录 · 系统数据」之前）：

```markdown
## 附录 · 学习记录

- 主题：Python｜时长：45min｜来源：self｜产出：笔记-asyncio
- 主题：系统设计｜时长：30min｜来源：course｜产出：章节3
```

2. `python -m review_tool ingest` → `learning_logs`，并重建 `review_queue`
3. 查看：`python -m review_tool tutor`（今日待复习 + 本周主题/投入/产出物）

| 项 | 规则 |
| --- | --- |
| 主题 | `config.LEARNING_TOPICS` 命中用规范 key；否则 `slugify` |
| 来源 | `clickup` / `self` / `course`（中文别名：手填 / 课程 / 成长课） |
| 队列 | stage 由历史学习次数推算；间隔 1/3/7/16；可从 logs 完全重建 |
| 与四维 | **不参与**（G5） |

证据链素材：`python -m review_tool clickup --list 901422213138`（v1.24.0 起成长课与书单已并入日常事务）。
讲解 / 出题交给对话现场能力，不落库。

⛔ 禁止「只进库不落 md」。

## 4. 生成「七、AI 评价与建议」

先取确定性上下文，再据此撰写：

```bash
python -m review_tool ai-context YYYY-MM-DD     # 当日事实 + 近 7 日均值 + 规则命中的关注点
```

| 部分 | 要求 |
| --- | --- |
| **评价** | 2–3 条，覆盖「做得好」与「需留意」，**必须引用上下文里的真实数字**（如「睡眠 7.17h、质量 89」） |
| **建议** | 2–4 条可执行动作，带**时间锚点或目标值**（如「22:30 手机放客厅，目标 23:30 前熄灯」「碳水补到 220g」） |

⛔ **不得编造上下文未列出的数据**；上下文没覆盖的日期或指标不要臆断。

- ⚠️ **`ai-context` 里没有「熔断」**（它只给「连续 N 天…」这类规则命中）。撰写前**另跑一次**
  `python -m review_tool doctor`，看 `[熔断检测]` 的 🔴 / ⚠️ 行与 `[相对基线]`，把它们写进「评价」。
- 📌 **熔断看的是「连续计数」，拐点在第 3 天**：单日系统分只差 0.25（如 2.0 → 1.75）也可能从
  「无熔断」跳到「两条 🔴」。日报必须点名 —— 否则用户只看到分数小抖动，看不出质变。
- 📌 连续多日同一形状时（如连着几天「只有游戏、三维全 1 分」，屏幕逐日新高），
  **评价要写出趋势而不是复述当日数字**：引用「连续 N 天」+ 与前一日的对比（如「9h54m 占 60.8%，
  9/26 尚为 3h58m」），建议要给**可执行的最小动作**（如「午餐后 30min 手机放抽屉」）。
排版：`**评价**` 用无序列表；`**建议**` 用 `1. **加粗引领**：…` 编号列表；**都不用表格**。

## 5. 格式规范（强制）

- 标题：`# 每日复盘 · YYYY-MM-DD（星期X）` —— **星期一律写全称**（星期一…星期日）
  （这是 v1.3.3 定版的项目规约；历史上用单字的都已被标准化，别再写回单字）
- 章节顺序固定：一、日常打卡 → 二、今日三件事 → 三、一个改进点 → 四、明日 Top 3 →
  五、时间投入 → 六、四维评分 → 七、AI 评价与建议 → 附录 · 系统数据
- 一、日常打卡：`**晨间（起床后）**` + `- [x] 补剂…` **嵌套勾选列表**，不用表格
- 五、时间投入：三行 `- 深度工作（h）：N`，各带 `← 对应数据块` 尾注
- 六、四维评分：表格 `| 维度 | 分数 | 状态 | 待补字段 |`
- 缺「七、AI 评价与建议」= 当日确实没有 AI 建议（内容事实），**不补空占位**
- 完整模板见仓库根目录 `每日复盘模板.md`，不一致时以它为准

## 6. 收尾回复

简短告知：**处理了哪一天**、**回填了哪些数据/素材**、**生成了哪个文件**（完整路径）、
**给了几条评价与建议**。然后按项目 5 步协议写执行摘要（见 `dailylumen-conventions` §7）。

## 7. 与项目规约的衔接（别踩）

- 改了评分规则 / 想调口径 → 走 CLI（`recompute-scores --apply` + `sync-docs`），
  不要为了「看起来对」去手改 md 里的分数（下一次 CLI 跑动就归位）
- 训练日**没填 = 没练**（若当天确实做了徒手训练但只在「二、今日三件事」写了动作，
  系统会按 `config.BODYWEIGHT_MOVES` 自动折算运动时长；想自己控制就在数据块填 `运动时长_min`）
- 补了历史某天的数据 → 重跑 `ingest`，再 `doctor` 看「打卡对账 / 分数一致性」是否干净
