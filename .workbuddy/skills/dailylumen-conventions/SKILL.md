# DailyLumen 项目口径与工程约定

> 本文件是**项目级方法资产**，随仓库入 git、随 tag 走版本 —— 换机 `clone` 即得。
> 本机专属的环境坑（写盘 / git 引用 / 缓存脏）不在这里，而在**不入 git** 的
> `.workbuddy/memory/MEMORY.md`，因为那些是"这台机器"的属性，不是项目的属性。

## 适用场景（何时加载）

任何要**动这个仓库**的会话：改 `review_tool/` 代码、改评分规则、批量改复盘 md、
动 `reviews.db`、发版本、换机迁移。加载后按下面的口径执行 ——
**别凭直觉重新定义口径**，这个项目里几乎所有"看起来该这么改"的地方都有历史拍板。

## 0. 范围边界（先划清）

- **本项目 = 个人健康 / 复盘系统**：md 复盘 → `review_tool` → `reviews.db` → 评分 / 熔断 / 报告。
- ⛔ **不混"重装备份 / win-reinstall-toolkit"那套** —— 那是跨项目基础设施，与本系统**相互独立**。
  不要在本仓库文档里引用备份脚本，也不要把本仓库内容写进备份清单。
- **运动主数据源（v1.21.0–v1.26.0 / M17–M20）**：练练健身 API → `keepstrong` 素材 → `--write` 落 md → `ingest`（G1）；写回（`--set-weight` / `--log-body` / `--schedule`）须 `--yes`，不落库。**M20 起**训练日主判据 = 被复盘日 `status=="completed"`（`training_weekdays` 仅离线兜底）。**M21 / v1.27.0** 起 `coach` / `steward` / `doctor` 不再把星期兜底写成「应为 / 休息日 / 计划课次」。
- **行为跟踪执行层在 ClickUp**（个人行为 / 习惯 / 年度目标 / 书单）：素材仍单向供给复盘；
  **v1.15.0 / M11 起**，「习惯与打卡」另有一条受控写库：ClickUp → `habit_logs` 快照
  （**唯一 ClickUp→库写方向**，不参与四维评分）。空间结构、list ID、映射口径、日期归属
  （`date_closed`，含「次日早上补勾」回拨）与「两套打卡体系不许混」的边界，见 skill
  **`clickup-tracking`**。
- **不在本仓库的资产**：助手人格 / 协作准则在用户级记忆 `~/.workbuddy/MEMORY.md`；
  跨项目通用 SOP 在用户级 `~/.workbuddy/skills/`（`sqlite-safe-migration`、`nmpa-cosmetic-record`）。
  用户级资产怎么保管**不属本仓库职责**，本仓库只保证项目级 skill 随代码入库。

## 1. 权威归属（最重要的一条，先记它）

改数据前先问"这件事谁说了算"。四类对象四个权威，混了就会互相覆盖：

| 对象 | 谁说了算 | 怎么收敛 |
| --- | --- | --- |
| 四维分 / 系统分（数据块 + 「六、四维评分」表） | **数据库** | `recompute-scores --apply && sync-docs`；⛔ **绝不手改 md 里的分数** |
| 打卡勾选（`personal_tracks`） | **源 md** | `doctor [打卡对账]` 检测 → `ingest --prune-tracks` 清理（默认关闭） |
| 一般字段（睡眠 / 时长 / 热量 / 结论文本…） | **源 md** | `ingest` 重新入库；upsert 默认 COALESCE 不擦数据 |
| 食物明细（`nutrition_items`） | **源 md（整表替换）** | 该日明细 = md 附录那张表，`ingest` 先删后插；无天然主键靠 `seq` 定序 |
| 口径本身（分档 / 阈值 / 熔断参数） | `config.py` | 改完**必须**重算 + 回写文档，否则库与文档分叉 |

**为什么分数必须归库**：文档里的分数是派生值，写入端与人读端双向可写 ——
规则一改、库按新口径重算，下一次 `ingest` 又被文档里的旧值覆盖回去，口径变更无法生效。
`sync-docs` 把两处一起渲染成库值，双向覆盖问题才根除。

- 🔴 **叙事段里的手写分数：不改写、只加注**。`sync-docs` 只渲染数据块与「六、四维评分」表，
  **正文叙事（「七、AI 评价与建议」、`一句话总结` 等）是人写的，口径换代后不会自动更新** ——
  它们会静默停留在旧标尺的数字上（实例：`2026-10-20` 正文写「学习 2.45h 拿 7 分」，
  v2 标尺现算 **9 分**；同句「近 7 日均值 4」现算 **5.0**）。处理原则：
  - ⛔ **不改写原句** —— 那是当时的真实表达，改了就失真；
  - ✅ **在数字旁加括注**：`拿 7 分（…；v2 标尺现算 9 分）`，让以后回看知道这是哪代标尺；
  - ✅ **只在真会回看时补**（写复盘当时发现、或回看某天时顺手补）；
    ⛔ **不做全库扫描** —— 78 天里多数天并没写具体分数，扫一遍的成本远高于收益；
  - ⚠️ **改完要 `ingest <该 md>`**：`一句话总结` 落在数据块内、权威在源 md，
    不重新入库会让 md 与 `daily_reviews.summary` 分叉。

## 2. 评分与熔断口径（标尺 v2，v1.34.0 定版）

- **时长三维用锚点插值，不用分档**：`config.SCORE_THRESHOLDS[*]["anchors"]`
  = `[(小时, 分值), ...]`，区间内线性插值、两端封顶。
  ⛔ **别退回分档** —— 分档必然产生空档（旧标尺分值集合只有 `{1,2,3,4,5,7,9}`，
  6 分不可达、10 分不存在，「及格 6」实为「必须踩 good 档」）。
  现行锚点：工作 `2h=5 / 4h=7 / 7h=10`；学习 `0.5h=4 / 1h=6 / 3h=10`；
  生活 `1h=5 / 2h=7 / 4h=10`。
- **健康子项用阈值分档**：`bands`（从优到劣）+ `floor`；`gte=True` 越大越好、
  `False` 越小越好。三处曾是死档（入睡 89% 同分 / 屏幕 74% / 运动 69%），
  已分别细分为「延迟轴八档」「九档」「区分 0min 与 >0」。入睡用**距 22:30 的延迟轴**
  而不是钟点（跨午夜不跳变）。
  ⛔ 改配置时**不许写出两个档同分** —— `test_bands_have_no_duplicate_scores` 会炸。
- **系统分 = 四维算术平均**（四维齐全才算，2 位小数）。它**只做纵向趋势，
  不承担绝对及格判断** —— 上限实测只有 6.5（时间预算零和：6+3+3+8 = 20h，
  剩 4h 装通勤三餐）。要看「哪里拖后腿」用 `weakest_dimension` / `balance_spread`
  （`stats` 已渲染短板分布与均衡度）。
- **缺失子项**：整项剔除、剩余权重重新归一（健康为加权模型；时长三维为插值）。
- **取整用 `_round_half_up`**（`floor(v + 0.5)`），⛔ 不用 `round()` —— 银行家舍入会让
  `round(2.5) == 2`。
- **熔断**（`config.FUSE_RULES`，CLI `fuse`，有**未失效**的绝对熔断时 rc=1）：
  - 绝对 = 任一维度连续 `days`(3) 天 < `threshold`(6)；
  - 相对 = 近 `recent_days`(7) 日均值 vs 之前 `baseline_days`(28) 日均值，偏离 ≥ `drift`(1.0)；
  - 连续超过 `long_run_days`(14) 天 → 报告显式提示"绝对阈值对该维度已失去分辨力"，改用相对信号；
    **v1.33.2 起这类项不计入「熔断态」与 rc**（否则报告自相矛盾：一边宣称阈值失效，一边算作熔断）。
  - **别把两个信号当一回事**：绝对信号在"长期低分"分布上近乎恒真，分辨力来自相对基线。
- **`doctor` 口径唯一**：结论与退出码都走 `is_healthy()`；新鲜度 / 历史断更 / 分数一致性 /
  打卡对账 / 熔断 / **打卡依从率骤降**（v1.10.1，`TRACK_ADHERENCE_ALERT`）一律**建议性**
  （只提示不拦）。要加新体检项时，先决定它是否影响 `is_healthy`，别各写一套记账。
  控台 UTF-8：入口 `__main__.ensure_utf8_stdio()`（v1.10.1）优先固定流编码；仍失败时
  渲染层降级为 `[OK]`/`[!]`/`[x]`（v1.7.1），避免 GBK 控台炸。

## 3. 运动时长口径（v1.3.1–v1.3.2 定版）

- **训练日没填 = 没练**：`exercise_min=0` / `exercise_src='zero'`，**计入达成分母**（二态，无"未记录"豁免）；
  非训练日保持 `NULL`；手填 `0` 记 `'record'`（明确记录 ≠ 口径兜底）。
- **描述折算**：md「二、今日三件事」命中 `config.BODYWEIGHT_MOVES` → 确定性模型折算
  （净执行 + 组间休息，单日 clamp 10–45min），`src='derived'`。
- ⛔ **只扫「二、今日三件事」**，不扫「七、AI 评价与建议」（后者会引用别的日期，
  真实误判来源：9/20 评语写"你在 9/19 做过 100 个俯卧撑"）。「一个改进点 / 明日 Top 3」也不扫 —— 那是计划不是记录。
- **字段优先、不叠加**：`运动时长_min` 已有数值时以字段为准，折算不生效。
- `exercise=0` 时健康分的运动子项按**差档**计（不是整项剔除）—— 这是确定性结果，别当 bug 改。
- 🔴 **改 `training_day` 不是改元数据，会连锁改分数**：`ingest.fill_exercise_zero` 对
  「训练日 + 运动未记录」补 `exercise_min=0`，于是运动子项从**整项剔除**变成
  **0 分计入分母**，健康分随之下落 —— 实例：09-15 修正为训练日后健康 5→4、
  系统 5.00→4.75。⚠️ **空值剔除会让该日健康分虚高，这才是「改对了反而降分」的原因**，
  不是回归；反之该日运动已 ≥ `train_ok`(10min) 时改标记不改分（如 09-22 的 10min
  在训练日与非训练日同为 6 分）。
  → 修完**必须** `recompute-scores --apply && sync-docs`，并回头同步周报 / 月报里
  受影响的四维均值、`system_avg` 与训练日达标率（**分母与分子都会动**）。
- 🔴 **训练日判定源（M20 起定版 · 2026-10-16 用户拍板）**：`training_day` 的**主判据**是
  练练健身在**被复盘日**的 **`status == "completed"`** 记录（其余状态一律排除；
  **系统不做延期补偿** —— 练练「未完成自动延期一天」是 App 内行为）。
  `config.PROFILE["training_weekdays"]` **仅作离线兜底**（拉不到练练数据时），
  且输出**必须明示是兜底**，否则无法区分「真没练」与「拉不到」。
  对象日 = **被复盘日**（= 复盘执行日的「昨日」），⛔ 不是执行日当天。

## 4. 文档规约（v1.3.3 定版）

- **统一现行模板**：`一、日常打卡 … 六、四维评分 / 七、AI 评价与建议 + 附录 · 系统数据`；
  `星期` 一律写全称（星期一…星期日），标题同步。
- **语雀导入件（`2026-07/*` + `08-04`）保留九段式原文附录**，不强套新模板（会丢工作/学习/生活/偏离分析）；
  其现行形态即转换口径；但**数据块仍随库同步**。
- **缺「七、AI 评价与建议」= 当日无 AI 建议**（内容事实），不补空占位。
- **目录职责**：`复盘/YYYY-MM/` 是标准源（`ingest` 只扫这里）；`收件箱/`、`历史源复盘/`
  不参与 ingest，各带 README 说明。
- **批量改文档** → 用 skill **`doc-corpus-normalize`**（探测 → parse 基线 → dry-run → apply →
  逐字段 diff → 入库后快照比对），别直接批量替换。
- 🔴 **周报 / 月报 / 周总结都不在 `sync-docs` 覆盖范围内**（它只渲染日 md）。所以：
  - 出周报**必须先跑 `python -m review_tool week <ISO周>`**，对比表 / 四维均值 / 客观指标**一律以它为准**，
    ⛔ 不要抄上一份周报里的数字 —— 分数口径（分档 / 阈值）改过之后，旧周报会静默停留在旧值
    （实例：`周总结-W37` 的系统分先后出现过 **4.89 / 4.54 / 4.82** 三个值 —— 分别是
    「手写算错」「v1 标尺库值」「v2 标尺库值」。同一周三个数，正说明旧值一律不可复用）。
    v1.7.2 起 CLI 会附带「个人打卡依从率」（按 `item_key`；**不计入四维**）。
    v1.8.0 起可用 `week <N> --write` / `month <YYYYMM> --write` 落结构化骨架
    （叙事段仍手写；默认不回填旧件，覆盖需 `--force`）。
  - 「连续 N 周垫底 / 全周期最低 / 最长全勤」这类断言**必须用脚本复算**（SQL + `FUSE_RULES`），
    不能沿用旧周报结论 —— 口径一变，排名和极值都会翻。
  - 文件命名 `周总结-W<ISO周>-YYYY-MM-DD_MM-DD.md`，落 `复盘/YYYY-MM/`（与当周首日同月）。
- 🔴 **月报同理**：出月报先跑 `python -m review_tool month <YYYYMM>`；
  实例：`月总结-202608` 曾写「系统 4.82」（v1 标尺下是 4.08），**标尺 v2 现行值是 4.27**
  —— 做同比时不能用旧月报的数字直接相减。
  命名 `月总结-YYYYMM.md`，落 `复盘/YYYY-MM/`。
- 🔴 **回填旧周报 / 月报**（口径变更后补齐历史）—— 五条必做：
  1. 逐份跑 `week <ISO周>` / `month <YYYYMM>` 取现行值，**一个字都不抄旧文件**；
  2. 极值断言必须脚本复算：8 月月报回填时「最佳日 08-04」「最差日 08-26」全被推翻
     （→ 08-27 / **08-19**），W37 的「学习连续 3 周垫底」也不成立 —— 标尺 v2 下
     W36 的健康与学习**并列 3.71**，W37 才是学习第一次单独垫底（W35 最差维度是**健康 3.29**）；
  3. **别漏掉引用它的文件** —— 后续周报 / 月报里常写有「XX 文件是旧口径、请勿相减」的提示，
     回填后这些提示会变成误导，要一并改成「已回填、可直接对比」
     （实例：`周总结-W38` / `W39` 的 ⚠️ 口径提示、`月总结-202609` 的 8 月同比说明与训练日锚点）；
  4. `system_avg` 是**四维齐全日系统分的均值**，≠「四维各自均值再平均」
     （W35：4.46 vs 4.49 —— 该周 7 天里有 1 天缺维，两个口径就会分叉）；
     月度极值同样只在四维齐全日里比；
  5. 周 / 月训练日分母来自 `training_day` 字段，`doctor` 报的标记异常会让分母偏小，
     报告里要注明。**现状**：09-15 / 09-22 已于 2026-10-02 修正（连锁影响见 §3），
     **08-17 / 08-18** 已于 2026-10-14（v1.10.1）按约定修正（健康 5→4；08-18 系统 5.00→4.75）。
  6. **写「全周期最高 / 最低」前，先查是否存在 `data < 7 天` 的周** —— 库里 W29/W32
     这类周只含 2~3 天，它们在「周均」口径下会污染极值
     （实例：W40 屏幕 12.93h 是最高**完整周**；而 W29 只有 3 天、单日最高 15.33h，
     「周均」反而被拉成 9.14h，拿去评「最低周」就会误判）。
     要么把结论限定为「完整周最高 / 最低」，要么在正文注明该周天数。
     同理，**手写均值就别写**：把 7 天分数相加除 7 的工作交给脚本，人工很容易漏掉
     序列里的高点（W41 两次踩：漏算 10-05 的 4.00、把两天的生活分 9 写成一天）。

## 5. 数据库规约

- **SQLite `reviews.db` 是唯一数据源**；schema 走 `PRAGMA user_version` 幂等迁移（当前 **v11**）。
  v1.9.0 决断：`energy` / `mood` **保留**（不参与四维评分），不做破坏性删列。
  ⚠️ **v1.37.0：`commute_done` 已废弃**（通勤固定 2×2.4km/日，79 天填 18 天，
  那个 22.8% 只反映「懒得填」）。模板已删该行、周报月报不再渲染；
  **列与解析保留**（老 md 仍能入库），⛔ 不要在任何新报告里再引用它。
- **承诺对账（v10 / M29）的口径是红线**：`promises` 存「改进点 / 明日 Top 3」，
  兑现判定**只认次日结构化字段**（`learn_h`/`exercise_min`/`fat_g`/`bedtime`/
  `deepwork_h`/`phone_h`/`personal_tracks.done`）。判不了记 `unmapped`、
  次日没写复盘记 `no_data` —— **两者都不算未兑现**；兑现率只在可判定子集上算；
  **不进四维评分、不加惩罚**。⛔ 别用「承诺文本里出现某词」当兑现证据（只证明提过）。
  入口：`python -m review_tool promises`；周报第八节；`doctor` 的 `[承诺覆盖]`。
- **「今天不设」是决定，不是空转**（v1.37.0 / D1）：写 `- 今天不设` → `bucket='declined'`
  → 状态 `declined`，**不进兑现率分母**，也不判 `no_data`（它是当天的决定，不用等次日）。
  `doctor` 把「明写不设」与「空白」分开报 —— **别把两者混成一个数**。
  ⛔ 模板的填写提示必须放 `>` 引用块；写成 `-` 列表项会被当成承诺（42 天数据污染就是这么来的）。
- **ClickUp 只是旁证，不是判据**（v1.37.0 / M30，schema v11 `clickup_done`）：
  三条硬约束 —— ① **整张工时表都是本人执行记录，`is_self` 恒 True**
  （姓名位是「任务下发人」不是执行人 —— v1.37.0 曾按姓名位排除同事前缀，
  把 8-20 之后几乎全部工作流水都排除了，v1.37.1 废除该口径；也**不看 assignee**，
  工作 list 704 条 assignee 全是本人）；② **工时求和 ≠ 工作时长**
  （任务级估算会重叠，实测一天一百二十一条合计 57h），只取最长单条当下界；
  ③ **不做「承诺文本 ↔ 任务名」语义匹配**，硬做只会造出猜出来的兑现率。
  入口：`clickup-pull`（写快照）/ `clickup-done`（读某天完成了什么，写复盘时用）。
- **改 CHECK 只能重建表**，重建必须走全覆盖流程：
  备份 → 副本验证 → 显式事务 → 逐列 diff → 落真库（详见用户级 skill `sqlite-safe-migration`）。
- **`reviews.example.db` 必须与当前 schema 同版**（`tests/test_example_db.py` 守卫），
  否则新用户复制后首次 ingest 会被 CHECK 拒绝。
- schema 外的遗留列迁移时按**列交集**搬运，数据留档 `.workbuddy/backup/`；不存中间计算产物。
- **`reviews.db` 可从 git 里的 md 100% 重建**（实测 72 天 / 504 打卡逐字段 0 差异，
  2026-10-15 于 M9–M15 收口后复验；唯一例外是 `ingested_at` 这类「入库时刻」元数据列）——
  所以库里出现疑问时，最有用的动作是"从零重建再逐字段比对"，而不是盯着真库猜。

## 6. 工程约定

- **零依赖**：纯标准库。测试用 `unittest`（**24** 子命令；测试数以 README / 全量跑为准），`ruff` 在 `envs/default/Scripts`（托管 python 里没有）。
- **CI 是阻塞的**：从仓库内 md 从零重建数据库 → `doctor` / `recompute-scores` / `sync-docs --check`
  **阻塞**（对账干净、分数与字段重算一致、md 无需回写）；`fuse` 不阻塞（人生指标告警）。
  矩阵 3.10–3.13。
- **四层架构（v1.5.0）**：`core`（零 I/O 纯规则）→ `storage`（SQLite 唯一出入口）→
  `pipeline`（md ↔ 库）→ `reports`（读库产出）。依赖**只能自上而下**，
  由 `tests/test_architecture.py` 用 ast 强制；`import sqlite3` 只准出现在 storage；
  `config.py` / `settings.py` 留包根（可配置层，历史文档引用不失效）。新增模块必须归入对应层。
- **配置分层（v1.20.0 / M16）** —— 四层不许混：
  | 层 | 放哪 | 例 |
  | --- | --- | --- |
  | **凭据** | 仓库根 `.env`（gitignore；模板见 `.env.example`） | `KEEPSTRONG_API_KEY` / `CLICKUP_API_KEY` |

  ⚠️ **凭据会过期，且过期表现是「静默无数据」不是报错崩掉**（2026-10-21 实测）：
  `keepstrong` 返回 `401 apiKeyExpired` → CLI 打一行提示就**正常退出**，
  只留一句「离线兜底…」。这类失败不会让任何测试变红，容易被当成「本来就没数据」。
  - 处置：练练 App → 我的 → 连接 AI → 生成新 API Key → 写入 `.env`；
  - **诊断顺序**：先 `keepstrong --date <D> --type body --stdout` 看是否 401，
    再去怀疑代码 / 数据。
  - 同一现象也会出现在**从没跑过同步**上：`body_metrics` 0 行既可能是无数据，
    也可能是链路从未触发 —— 两者要分开验证（看 md 数据块有没有 `体重_kg` 值）。

  **技能文档（2026-10-21 补充）**：上游是 `GET /api/v1/ai/skill`（Bearer 认证），返回的
  JSON 才是接口契约的权威源，本地两处落地：
  - `docs/练练健身-API参考.md` —— 中文规格，给人看（**不含密钥**）；
  - `.workbuddy/cache/keepstrong-skill-<ver>.json` —— 原始 JSON 快照，给机器看（gitignore）。
  每个非 skill 请求都必须带 `X-KeepStrong-Skill-Version` 与 `X-KeepStrong-Agent-Name`；
  服务端返回 `426 skillUpdateRequired` 就重新拉、重存、改 `settings.DEFAULT_KEEPSTRONG_SKILL_VERSION`。
  ⛔ **拉文档本身也要用 Key**，所以 Key 过期时连规格都拿不到 —— 换 Key 是第一步不是最后一步。
  | **环境差异** | `.env` 可覆盖，代码给默认值（`settings.Settings`） | baseUrl / timeout / `DAILYLUMEN_DB_PATH` |
  | **个人参数** | `config.PROFILE` 等（**入 git**） | 身高 / 宏量目标 / 训练日 |
  | **业务规则** | 代码 | `SCORE_THRESHOLDS` / `FOOD_LIB` / `COACH_RULES` |
  ⛔ **不引 Pydantic / python-dotenv** —— `review_tool/settings.py` 用标准库
  `dataclass` + `os.environ`；`config.py` 是门面（既有名字全保留）。
- **CLI 参数单一来源**：`__main__.py` 是**纯路由**（`ROUTES` 表 + 原样透传 argv），
  参数只在各模块 `main(argv)` 里定义一次；顶层统一拦截 `<子命令> -h`
  （否则 `ingest -h` 会真的跑一遍入库）。
- **文档分工**：`README.md` 讲怎么用；`docs/设计说明.md` 放规则 / 口径 / 字段 / 变更日志；
  `docs/迁移指南.md` 讲换机；`review_tool/README.md` 是包级速查。
- **版本节奏**：语义化 commit **逐 feature 单独提交** + 打 tag（小幅 `x.1`，重大升级主版本 +1），
  `main` fast-forward 推 GitHub（`deTian0/DailyLumen`）。每轮收尾都要更新
  `pyproject.toml` / `review_tool/__init__.py` / `README.md` 版本头 / 变更日志，四处对齐。
- 🔬 **「假装自己是 CI」演练**（挖漂移最有效）：删库或建临时库 → 用源 md 从零重建 →
  与真库**逐字段逐行**比对（不只看日期集合）。v1.4.2 的 17 条陈旧打卡键就是这么挖出来的。

## 7. 交付流程（5 步协议）

> ⏱ **复盘节奏（2026-10-19 改版）**：复盘**当晚睡前写当天** —— 10-19 晚上写的就是 10-19 的复盘。
> md 文件名与数据块日期一律写**当天**。取代 2026-10-15 的「次日晨间回顾昨日」。
> 当晚写时 `手机屏幕_h` 记截至写稿时的实时值（非 24:00 终值），次日可回填补正。
> 细则见 skill `daily-review-intake` §0。
>
> 🌙 **睡眠归属 = 醒来日（v2，2026-10-19 用户拍板）**：第 N 天的睡眠 = 第 N−1 晚 → 第 N 天早上，
> 截图标注日**原样即归属日、不再 −1**。旧口径（入睡日 / 截图日 −1）只用于 10-15 及以前，
> **不做全量平移**；切换点在 **10-16 留空一处**（该夜已计入 10-15），10-17 起按新口径。
> 表格与理由见 skill `daily-review-intake` §2.1 —— 别按直觉重新发明一遍。
> ⚠️ 这两个改动是配套的：当晚写当天之所以可行，正是因为睡眠按醒来日归属、早上数据就已闭环。
>
> 📥 **素材投递方式（2026-10-20 用户定版）**：六类素材（睡眠 / 饮食 / 屏幕 / 三个时长 /
> 打卡 / 可选体征）**每晚睡前一次性发来，可并成一条消息，有一项算一项**。
> **不再逐项催收**；缺项留空、⛔ 不估算、⛔ 不把「没提」当「做了」。
> 映射表与理由见 skill `daily-review-intake` §0.5。

1. **读 memory** —— `.workbuddy/memory/MEMORY.md`（本机坑 + 指针）+ 最近日志
2. **执行** —— 按本 skill 的口径动手；每步之后**复核**（文件计数 / parse 基线 / 快照 diff）
3. **输出** —— 结论先行、表格 + 文件定位、简明中英混排
4. **present_files** —— 把新产出的交付物推给用户看
5. **写执行摘要** —— 追加到 `.workbuddy/memory/YYYY-MM-DD.md`（append-only）

## 10. 易踩的坑（工程类，机器无关）

1. **`.gitignore` 整目录规则会让白名单静默失效**：必须写 `.workbuddy/*` + `!.workbuddy/skills/`。
   写成 `.workbuddy/` 会连目录一起排除，git 不再向下遍历，`!` 规则不报错也不生效。
   `tests/test_repo_layout.py` 把这条钉死了 —— 别"顺手清理"回去。
2. **改文件别用 Python 的文本模式写**：`open(p, "w")` 会在 Windows 上把行尾改成 CRLF，
   而 `.gitattributes` 要求 `eol=lf`。用 `open(p, "rb"/"wb")` + `replace(b"\r\n", b"\n")`。
3. **改服务端权威字段 = 白改**：md 里的分数、`ingest` 能覆盖的普通字段，改 md 只是临时状态，
   下一次 CLI 跑动就归位 —— 要改请改 `config.py` / 代码再走 CLI 收敛。
4. **`upsert_personal_track` 只增不删**：规范 ID 一改（如裸 `movefree` → `movefree@noon`），
   旧键永久滞留并**重复计依从率**。动的打卡项就要想着跑对账。
5. **`ingest` 只处理第一个路径参数**：`main()` 里是 `for p in [args[0]]`，多传的路径
   **静默丢弃**（不报错、不提示）。要入多份就分次调用，或直接跑全量 `ingest`。
6. **`raw_path` 会被写入值覆盖**：它列在 `_ALWAYS_OVERWRITE`，而 `parse_file` 直接存
   传入路径 —— 用**相对路径**跑 `ingest` 会把库里的绝对路径改写成相对路径，而
   `doctor` 的 `os.path.exists(path)` 在项目根执行时照样通过，**不报错**（静默污染）。
   单独补录某天时传 `os.path.abspath(p)`；判据是跑完 `IS NULL` 之外的行数是否为 0。
7. **本机专属的坑不写进本文件**：写盘不落盘、`git update-ref` 报成功不生效等属于
   "这台机器"的属性，记在 `.workbuddy/memory/MEMORY.md`（不入 git）。换机后若不复现就删掉。
   对应的**可执行动作**见用户级 skill `safe-write`（写后回读校验 + git 引用核对修复）。
