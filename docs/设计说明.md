## 📊 评分规则（核心）

四维评分：**健康 / 工作 / 学习 / 生活**，各自 1–10 分；**系统分 = 四维均值**  
（四维齐全才计算，保留 2 位小数）。

入库时（`ingest.py`）若某维分缺失则自动生成——**只补 `None` 的，绝不覆盖手填值**。

### 1. 健康分（规则化加权，基于客观健康子指标）

健康分由各子指标加权求和得到。**任意子指标缺失则跳过该项，剩余权重重新归一化**；  
最终结果 clamp 到整数 1–10。

| 子指标  | 权重   | 评分标准                                                                  |
| ---- | ---- | --------------------------------------------------------------------- |
| 睡眠时长 | 0.18 | ≥8h → **10**（满分）｜≥7h → 8｜≥6.5h → 6｜≥6h → 4｜<6h → 2                    |
| 睡眠质量 | 0.12 | 0–100 线性映射到 0–10（quality ÷ 10）                                        |
| 入睡时间 | 0.15 | 00:00–05:00（熬夜到凌晨）→ 3｜≤22:30 → **10**｜22:30–23:30 → 8｜23:30–23:59 → 5 |
| 运动   | 0.25 | **训练日**：≥30min → 10｜≥10min → 6｜否则 2　**非训练日**：≥20min → 8｜否则 6          |
| 饮食热量 | 0.10 | 1200–2200 kcal → 8｜1000–1200 或 2200–2600（边界）→ 5｜其余 → 3                |
| 手机屏幕 | 0.15 | ≤4h → **10**｜≤6h → 8｜≤8h → 6｜≤10h → 4｜>10h → 2                        |

> 权重和为 0.95（服药依从已移出通用评分），缺失子项时剩余权重自动归一化。  
> 服药 / 护肤等个人定制项不计入通用健康分，单独统计于 `personal_tracks` 表。

> 入睡时间 `bedtime` 存「距 00:00 的分钟数」(23:47 → 1427，00:39 → 39)。  
> 跨午夜的凌晨时段（≤300 分钟）判断优先于当晚时段，避免命中 ≤22:30 拿满分。

### 2. 工作分（基于深度工作时长 `deepwork_h`）

**达标区**（≥ ok 线）三档步进，**未达标区**细分（v1.4.0，只影响 `2h` 以下）：

| 深度工作_h       | 工作分 | 档位   |
| ------------ | --- | ---- |
| ≥ 6h         | 9   | full |
| ≥ 4h         | 7   | good |
| ≥ 2h         | 5   | ok   |
| 1.5h – 2h    | 4   | 未达标区 |
| 1h – 1.5h    | 3   | 未达标区 |
| 0.5h – 1h    | 2   | 未达标区 |
| < 0.5h（含 0 ） | 1   | 未达标区 |

### 3. 学习分 / 4. 生活分

规则与工作分同构，阈值分别取 `learn_h` / `life_h`：

| 投入_h          | 分数 | 档位   |
| ------------- | -- | ---- |
| ≥ 3h          | 9  | full |
| ≥ 2h          | 7  | good |
| ≥ 1h          | 5  | ok   |
| 0.75h – 1h    | 4  | 未达标区 |
| 0.5h – 0.75h  | 3  | 未达标区 |
| 0.25h – 0.5h  | 2  | 未达标区 |
| < 0.25h（含 0 ） | 1  | 未达标区 |

> **为什么要细分未达标区（v1.4.0）**：49 天样本里学习分 **82% 的天数 <6、  
> 60% 正好落在最低档**。原先「`< ok` 一律 3 分」会让 0h 与 1.5h 投入无法区分  
> —— 49 天的趋势被压成一条直线，改善不可见，熔断信号也被地板吞掉。  
> 细分**只作用于未达标区**，`≥ ok` 的分值语义（5/7/9 = 踩线分）完全不变。
>
> 上下界在 `config.SCORE_THRESHOLDS[*]["sub_floor"/"sub_ceil"]`，默认 1 / 4。  
> 若觉得「周末没做深度工作 = 1 分」过重，把 `work` 的 `sub_floor` 调到 2 即可。

### 5. 系统分

```
系统分 = round((健康分 + 工作分 + 学习分 + 生活分) / 4, 2)
```

四维中任一缺失则不计算，留空。

### 6. 熔断规则（`fuse`，v1.4.0 才真正落地）

用户原始定义：**任一维度 <6 连续 3 天 → 熔断**。此前这条规则**只写在文档里、  
代码零实现**（7 月复盘正文甚至写着「aggregate 会主动标红」，而那个 aggregate  
是语雀时代的旧流程，从未迁进本工具）。结果：学习维度连续 24 天 <6，系统一声不吭。

`python -m review_tool fuse` 现在给出**两个信号**：

| 信号   | 定义                                                                    | 作用                 |
| ---- | --------------------------------------------------------------------- | ------------------ |
| 绝对熔断 | 任一维度连续 ≥`days`(3) 天 <`threshold`(6)                                   | 用户原始定义的规则          |
| 相对基线 | 近 `recent_days`(7) 日均值 vs 之前 `baseline_days`(28) 日均值，偏离 ≥`drift`(1.0) | 真正有分辨力的「在变好 / 在变差」 |

**为什么必须有第二个信号**：49 天样本里学习分 82% 的天数 <6、60% 正好落在最低  
档 —— `<6 连续 3 天` 在这条分布上近乎恒真。所以连续超过 `long_run_days`(14)  
天时，报告会显式提示「**绝对阈值对该维度已失去分辨力**」，而不是继续刷同一条告警。

首次运行的真实输出：

```
[绝对信号 · 已触发]
  ⚠️ 学习：连续 24 天 < 6（自 2026-08-29 起）｜超阈值 8.0 倍
  🔴 生活：连续 11 天 < 6（自 2026-09-11 起）｜超阈值 3.7 倍
  ⚠️ 系统：连续 24 天 < 6（自 2026-08-29 起）｜超阈值 8.0 倍

[阈值失效提示]
  ·  学习（连续 24 天）—— 请改用下面的相对基线判断

[相对基线] 近 7 日均值 vs 之前 28 日均值
  生活  4.56 → 3.0  ▼ -1.56  ← 变化明显
  工作  5.04 → 6.14  ▲ +1.10  ← 变化明显
```

阈值全部住在 `config.FUSE_RULES`（可配置层）。`doctor` 也会带出熔断小节。

## 🔒 分数的单一权威（v1.4.0）

**数据库是唯一权威，md 由它渲染。**

历史复盘 md 有两处分数呈现，都是**派生值**：附录数据块里的  
`健康分 / 工作分 / 学习分 / 生活分 / 系统分`（会被 `parse` 读回），以及  
「六、四维评分」表格。旧流程把它们写进文档后就不管了 —— 于是规则一改、  
数据库按新口径重算，下一次 `ingest` 又被文档里的旧值覆盖回去，  
**口径变更无法追溯生效**。

约定：

1. **分数不在数据块里手改** —— 它由 `sync-docs` 从库里渲染；
2. 改了 `score.py` / `config.SCORE_THRESHOLDS` 之后，跑  
   `python -m review_tool recompute-scores --apply && python -m review_tool sync-docs`  
   全库即刻统一（`recompute-scores` 默认只试算并列出差异，加 `--apply` 才落库）；
3. `sync-docs --check` 只报告差异不写文件，可放心先看；
4. **语雀九段式原文（标题带「（1 – 10）」）不在回写范围内** —— 保留原貌，  
   见 v1.3.3 的文档格式规约；其数据块仍会同步；
5. `doctor` 的 `[分数一致性]` 段会逐行比对「库中分数」与「按字段重算的结果」，  
   一旦有人手改了 md 分数、或规则变更后没重算，就会被点名（v1.4.1 新增）。  
   该检测**不影响 `is_healthy`** —— 手填覆盖属合法行为，只提示不拦。

## 📏 统计口径（v1.3.0–v1.3.2 三轮收口）

### 训练日运动：二态 —— 没填即没练（v1.3.2 终版）

口径经历三轮演进，最终定为**二态**：

1. v1.3.0 前：`exercise_min > 0` 直接判达标，「字段空着」被误判成「没运动」；
2. v1.3.0：拆成三态（达标 / 未达标 / 未记录），未记录单列不进分母；
3. v1.3.2（**终版**）：「未记录」豁免态废除——训练日没填就按 0 计  
   （`exercise_min=0`、`exercise_src='zero'`），计入未达标。

```
训练日运动 : 达标 2/4 天 = 50%（其中 1 天为描述折算，2 天未记录按 0 计）
```

- **达成分母 = 训练日总数**，不再存疑
- **达标** = `exercise_min > 0`
- **未达标** = `exercise_min = 0`（含「手填 0」与「未记录按 0 计」两种来源）
- 非训练日保持 `NULL`（运动不是当天的预期，不计入）


### 徒手训练折算：描述里提到动作就计入（v1.3.1）

折算解决的是三态时代遗留的洞：**你确实做了徒手训练，只是没填字段**。  
在「二、今日三件事」写了「做了二十个俯卧撑」，`运动时长_min` 却留空 ——  
按 v1.3.2 口径这天会被记 0，而实际运动了。运动占健康分权重 **0.25**，是全部子项里最重的一项。

现在描述里的动作会**自动折算**进运动时长（`exercise_src='derived'`）：

```
[入库] 复盘/2026-09/2026-09-21.md  ↳ 运动 10min 由描述折算
```

**折算模型**（定义在 `config.BODYWEIGHT_MOVES` / `BODYWEIGHT_RULES`）：

```
净执行时间 = 次数 / per_minute          （默认 20 次/分钟，即 1 次 ≈ 3 秒）
组间休息   = (组数 - 1) × set_rest_sec  （默认每组之间 60 秒）
单日结果   = clamp(Σ, 10, 45)
```

| 描述原文                | 识别结果         | 净计时     | 记入              |
| ------------------- | ------------ | ------- | --------------- |
| `俯卧撑 10 * 2`        | 20 次 / 2 组   | 2.0min  | **10min**（触发下限） |
| `10 * 10 个俯卧撑`      | 100 次 / 10 组 | 14.0min | **14min**       |
| `做了二十个俯卧撑`          | 20 次 / 1 组   | 1.0min  | **10min**（触发下限） |
| `今天做了一百个俯卧撑，分 10 组` | 100 次 / 10 组 | 14.0min | **14min**       |

支持阿拉伯数字与中文数字（`二十`/`一百`）、`A * B`（A=每组次数，B=组数）、  
`分 N 组` 等各种写法；`一组20个`、`一共20个` 里的「一」不会被当成次数。

**三个刻意的设计约束**

1. **单日下限取 10min**，因为健康分对空值子项是**整项剔除**（按剩余权重归一）——  
   如实记录一个很小的量反而比留空更吃亏（分母变大、均值被拉低）。取下限 10  
   （= 训练日「尚可」阈值）保证「如实记录」不会倒扣。
2. **只扫「二、今日三件事」**，不扫「七、AI 评价与建议」。后者会引用别的日期  
   （真实例：9/20 的评语写着「你在 9/19 做过 100 个俯卧撑」），扫了就会把别的  
   日期的量算到当天头上。「一个改进点 / 明日 Top 3」也不扫——那是计划，不是记录。
3. **字段优先、不叠加**。`运动时长_min` 已有数值时以字段为准，折算不生效，  
   避免同一份运动被计两次。

**想自己控制某天**：直接在数据块里填 `运动时长_min`（比如实际计时 35min），  
字段值会覆盖折算结果，来源标记也会变回 `record`。**想关掉某个动作**：把  
`config.BODYWEIGHT_MOVES` 里的对应条目删掉即可；想加动作（深蹲、平板支撑…）  
按同样结构追加一行。

报告与体检里折算来源是**可见**的，不会被混进计时记录：

```
训练日运动 : 达标 1/1 天 = 100%（其中 1 天为描述折算）
运动折算   : 3 天的运动时长由「三件事」描述折算（非计时记录）
```

> ⚠️ 该值仍是**估算**，来自确定性模型而非秒表。周/月报告、`ai-context` 与  
> `doctor` 都会显式标注「描述折算」，看数据时请自行扣减权重。

### training_day 兜底

`training_day` 空着时，入库会按 `config.PROFILE["training_weekdays"]`  
（默认周一/二/三/五/六）的日期约定兜底填充，避免这天从  
`WHERE training_day=1` 的统计里静默消失。

`doctor` 会提示「记录值与日期约定不符」的天数——那可能是临时调整训练日，  
属合理差异，**不算故障**。

### 数据完整度

周 / 月报告会输出核心字段完整度与缺失明细，避免只看百分比却不知道缺在哪：

```
数据完整度 : 83%（核心字段缺失: exercise_min×34、learn_h×15、life_h×15）
```

| 列                         | 含义                                  |
| ------------------------- | ----------------------------------- |
| `date` + `track_key` (PK) | 日期 / 规范 ID（含时段后缀，如 `coq10@morning`） |
| `item_key`                | 规范项 ID（不含时段）—— **按它聚合依从率**          |

`PRAGMA user_version` 记录 schema 版本，`init_db` 时自动逐级升级且幂等。  
当前版本 **4**：

| 版本 | 变更                                                                                                                                                         |
| -- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1  | `daily_reviews` 补齐宏量营养素列（`carbs_g` / `fat_g` / `protein_g`）                                                                                                |
| 2  | `personal_tracks` 主键从自由文本 `item` 改为规范 `track_key`，并回填历史数据                                                                                                  |
| 3  | `daily_reviews` 新增 `exercise_src`（`record` / `derived`），已有数值回填为 `record`                                                                                   |
| 4  | `exercise_src` 的 CHECK 放行 `zero`（训练日未记录按 0 计）。SQLite 改 CHECK 只能**重建表**：重建包在显式事务里保证原子（失败整体回滚），支持断点续迁（中断现场 `daily_reviews_v3_old` 自动恢复），schema 外遗留列按列交集搬运不阻塞 |

升级是**无损**的：迁移前会先校验（v1.3.0 实测 49 天数据逐行零差异），  
建议重大升级前先备份 `reviews.db`。

## 设计要点

- **SQLite 是唯一数据源**：通用结构化字段落在 `daily_reviews`；个人定制项单独落在  
  `personal_tracks`，不计入通用评分。
- **upsert 默认不擦数据**：新值为 `None` 时保留库中旧值，避免重跑 ingest 造成静默丢数据。
- **打卡归一化**：自由文本 → 规范 ID，让依从率可聚合（见上文专章）。
- **口径二态：没填即没练（v1.3.2 终版）**：训练日未记录按 0 计入未达标，  
  达成分母恒等于训练日总数；折算与手填优先于口径兜底，缺失数据不冒充有效值。
- **打分库为准、打卡文为准**：分数由库渲染到 md（`sync-docs`）；打卡反过来以
  源 md 为权威，`ingest --prune-tracks` 负责清掉规范 ID 变化后滞留的旧键
  （否则同一剂量会被重复计入依从率）。两者都用「有则对账、无则不动」的保守策略。
- **解析向后兼容**：` ```data ` 块 / HTML 注释块 / 纯文本表头三种格式，  
  以及历史上的「内核打卡」「零、日常打卡」「### 晨间」等写法都能识别。
- **防脏数据**：四维 1–10、质量 0–100、布尔 0/1、数值非负，均有 CHECK 约束拦截。
- **评分可解释**：健康分为客观子指标加权，工作 / 学习 / 生活分基于时长分档，规则全部透明。
- **零依赖**：纯 Python 标准库；CI 在 3.10–3.13 上跑测试与 lint。
- **CI 是阻塞的**：CI 会用仓库内 md 从零重建数据库，再要求 `doctor` 干净、
  `recompute-scores` 无差异、`sync-docs --check` 无待写 —— 口径回归会被立刻拦住。
- **可回退**：每个版本打 git tag，结构升级前先备份 `reviews.db`；一次性迁移脚本
  留档 `.workbuddy/backup/`（不入库）。
- **方法资产与代码同仓**（v1.4.3）：项目级 skill（`.workbuddy/skills/`）入 git 并随版本
  tag 走（`tests/test_repo_layout.py` 守卫白名单规则）；人格与跨项目 SOP 留在用户级
  （记忆 + `~/.workbuddy/skills/`）—— 两层各用对应机制，详见「工作区配置」。

## 变更日志

### v1.4.4 — 迁移指南（纯文档）

**新增 `docs/迁移指南.md`**：换机 / 重装后怎么把系统跑起来。

- 实测结论：**`reviews.db` 可从 git 里的 md 100% 重建**（49 天 / 343 打卡，
  逐字段 0 差异）→ 迁移不必手工搬库，`clone` + `ingest` 即可。
  实测方法即 `sqlite-safe-migration` 的「重建可复现性自检」。
- 明确「什么在 git / 什么不在」：不入库的只有 `reviews.db`、`.workbuddy/memory/`、
  `.workbuddy/backup/`、`exports/`、缓存；其中**只有 `memory/` 无法重建**，建议手工搬。
- 环境依赖：Python ≥ 3.10、**零第三方依赖**；代码无硬编码绝对路径
  （全部由 `config.py` 的 `__file__` 推导）→ 仓库放哪都行。
- 唯一依赖绝对路径的是**晨间收集自动化**（prompt 里写死了工作目录与收件箱路径），
  且其定义不在仓库里 → 换机必须手工重建并改路径。
- 附落地命令序列与换机后验证清单。README 的文档索引补入口。

**不改动程序**：零代码变更，行为与 v1.4.3 一致。

### v1.4.3 — skills 归类合并：方法资产入库 + 人格归位

**触发**：一次 skills 盘点发现 4 个自建 skill **全都不在版本控制内** —— 项目级不在 git
（`.gitignore` 整目录排除 `.workbuddy/`），用户级更在本仓库范围之外。

**归类（4 → 3，机制各归其位）**

| skill | 原位置 | 处置 |
| --- | --- | --- |
| `soul` | 项目级 | **并入用户级记忆** `~/.workbuddy/MEMORY.md` 的「协作准则」段，skill 删除 |
| `sqlite-safe-migration` | 用户级 | 保留 + 并入「假装自己是 CI」自检节 |
| `nmpa-cosmetic-record` | 用户级 | 保留 |
| `doc-corpus-normalize` | 项目级 | 保留 + 更新到 v1.4.2 事实 |

- **soul 为什么不该是 skill**：它声明「每次会话开始加载」是 **always-on 语义**，
  而 skill 是**按需加载**机制（由模型判断相关性），保证不了；且其协作准则段与本会话
  已注入的用户级记忆高度重复 —— 同一件事写了三处。用户级记忆是每会话无条件注入的，
  机制才对得上。项目专属的「连续性」段本来就在项目 `MEMORY.md` 里。
- **「假装自己是 CI」并入 `sqlite-safe-migration`**：该 skill 原本只证明「改动前后
  差异符合预期」，缺「**从源头重建能复现**」这一环 —— 而后者正是 v1.4.2 挖出
  17 条陈旧打卡键的手段。现作为独立小节并入，`doc-corpus-normalize` 引用它。
- **`doc-corpus-normalize` 更新**：步骤从一次性脚本 `.workbuddy/backup/normalize_docs.py`
  改为正式 CLI（`ingest` / `recompute-scores` / `sync-docs`）；补 v1.4.0 硬约束
  **「⛔ 分数不要手改」**（改规则请走 CLI，手改会被 `sync-docs` 覆盖，且 `ingest`
  又会把旧值写回库）、v1.4.2 的打卡对账、以及原未填的 `<skills>` 占位符。

**持久化（两层各用对应机制）**

- 项目级 → **入 git**：`.gitignore` 从整目录规则 `.workbuddy/` 改为 `.workbuddy/*` +
  `!.workbuddy/skills/`。原写法会把目录本身一起排除，git 因此不再向下遍历，
  **白名单静默失效**（不报错、不警告，只是文件不入库）——
  这是本轮最容易踩的坑，新增 `tests/test_repo_layout.py` 5 项守卫钉死。
- 用户级 → **本仓库不负责**：`~/.workbuddy/skills/` 与用户级记忆属跨项目资产，
  由本机自己的机制保管，不写入本仓库、也不在本仓库文档里展开。

**不改动程序**：本轮零代码变更，评分 / 解析 / 入库行为与 v1.4.2 完全一致。
**验证**：单测 283 → **288**（新增 `tests/test_repo_layout.py` 5 项：白名单规则 /
隐私目录仍忽略 / skills 目录非空 / frontmatter 完整 / name 与目录名一致）。

### v1.4.2 — 口径统一 + 打卡对账 + CI 阻塞自检

**背景**：v1.4.1 之后做了一次「假装自己是 CI」的演练 —— 删掉 `reviews.db`、
用仓库里的复盘 md 从零重建，再跑全链路。结果 doctor / sync-docs / recompute
全部自洽，但**打卡记录 343 条 vs 真库 360 条**，冒出 17 条对不上的行。

1. **打卡对账（新发现，已修）**：差异是真库里 17 条裸键 `movefree` ——
   源 md 里 Move Free 挂在午间/晚间小节（→ `movefree@noon` + `movefree@evening`），
   而 `upsert_personal_track` **只增不删**，v3→v4 迁移时代留下的裸键永久滞留，
   让同一剂量在 17 天里被**重复计 3 次**（污染依从率）。
   - `doctor` 新增 `[打卡对账]`：逐条比对库中打卡与源 md 勾选（只读、不拦）；
   - `ingest --prune-tracks`：以源 md 为权威集合清理陈旧键。**默认关闭**
     —— 删除不可逆，交由你显式触发；且仅当「一、日常打卡」章节确实解析到
     才执行（`parse.has_tracks_section`），避免把「解析失败」误判成「已删除」；
   - 已执行一次性清理：`360 → 343` 条，逐字段比对确认**除这 17 条外零变化**。
2. **doctor 结论与退出码同源**：此前 `render` 用自己的一套 `ok` 记账（把「超过
   1 天没补录」也算不健康），而退出码走 `is_healthy` —— 两者会打架。现在结论直接
   调用 `is_healthy`，并把新鲜度、分数一致性、打卡对账、熔断明确列为**建议性**；
   `is_healthy` 另加「库里至少有一条记录」。
3. **`week` / `month` 支持 `--json`**：先把数字收进 `analyze.collect()`，
   文本与 JSON 共用同一份数据（`render_summary()` 只管排版），口径不可能分歧。
   无数据时 JSON 模式保持 stdout 干净。
4. **`__main__` 改为纯路由**：原先顶层 argparse 与各模块 `main(argv)` 各写一遍
   参数，再由顶层「翻译」回 argv —— 两边不同步时新参数会被静默吞掉
   （这次加 `--json` 就当场撞上了）。现在参数只有一处来源（各模块自己），
   顶层只做路由 + 统一拦截 `<子命令> -h`（避免 `ingest -h` 真的跑一遍入库）。
5. **CI 阻塞化**：`doctor || true` 换成完整的端到端自检 —— 从仓库内 md 从零重建
   数据库，然后 `doctor` / `recompute-scores` / `sync-docs --check` **阻塞**
   （对账必须干净、分数必须与字段重算一致、md 无需回写）；`fuse` 仍不阻塞
   （人生指标告警）。新增覆盖率 job（仅 3.13）并把报告写入 job summary。
6. **文档拆分为「使用 / 设计」两册**：README 只留「怎么用」；评分规则、统计口径、
   字段速查、设计要点与变更日志移入本文件。拆分脚本按章节边界搬移并校验
   「非空行零丢失」。

**验证**：单测 252 → **283**（`test_cli.py` 9 项 + `--json` 5 项 + 打卡对账 10 项 +
doctor 口径一致 3 项 + parse 相关 4 项）；`ruff` 干净；CI 全序列本地跑通（doctor rc=0、
0 篇待同步、0 处重算差异）。

**库内结果**：`daily_reviews` 49 行**逐字段零变化**；`personal_tracks` 360 → 343
（仅删 17 条陈旧键）；schema v4、`integrity_check` ok 未变。

### v1.4.1 — 数据可信度加固（对账假阴性 / 分数漂移可见 / 空模板同版）

**背景**：v1.4.0 把「分数单一权威」立起来了，但三处「沉默的不可信」还没堵：  
① 对账用文件名里**第一段**日期，周总结 `周总结-W36-2026-08-31_09-06.md` 被  
当成 08-31 的日复盘 —— 日文档真缺失时反而报「一致」；② 库里的分数与「按字段  
重算」是否相符，此前**无从检测**（手改 / 漏重算都看不见）；③ `reviews.example.db`  
停留在 schema **v2**（缺 `exercise_src`、CHECK 不含 `'zero'`），新用户复制后  
首次 ingest 写 `zero` 会被 CHECK 拒绝。

1. **对账口径收紧（`doctor`）**：只认「文件名主干恰为 `YYYY-MM-DD`」的日复盘，  
   周 / 月汇总与带后缀的文件自然排除。修复是**预防性**的 —— 当前周总结的日期  
   恰好与日文档重合，所以历史报告没暴露过假阴性；新测试锁死该行为。
2. **新增 `[分数一致性]` 体检项**：逐行把「库中四维 / 系统分」与「按当前规则  
   从字段重算」的结果比对，列出不符明细。只读、**不参与 `is_healthy`**  
   （手填覆盖合法，只提示不拦）。
3. **`recompute-scores` 升格为正式子命令**（`recompute.py`）：取代原先散落在  
   `.workbuddy/backup/` 的一次性迁移脚本。默认**只试算并列出差异**，  
   `--apply` 才落库；口径与 v1.4.0 历史迁移一致（字段不足 → 置空，不保留旧手填）。
4. **`reviews.example.db` 重建到 v4**：空模板与当前 schema 逐列、逐 CHECK 对齐；  
   新增 `tests/test_example_db.py` 守卫（版本 / 列集 / `'zero'` CHECK / 空表 /  
   完整性 / 写入 `zero` 可接受），防止再次静默漂移。

**验证**：单测 225 → **252**（`test_recompute.py` 11 项 + `test_doctor.py` 新增  
分数一致性与对账 11 项 + `test_example_db.py` 7 项）；`ruff` 干净；  
真库 49 天 `[分数一致性]` 全部一致；`doctor` 结论仍为「数据健康」。

**库内结果**：真库未改动（`daily_reviews` 49 行、`personal_tracks` 360 条、  
`integrity_check` ok、schema v4 均未变）；仅 `reviews.example.db` 由 v2 重建为 v4。


### v1.4.0 — 分档细化 + 熔断检测落地 + 分数单一权威

**背景**：三个「规则存在但语义失真」的坑：① 时长分档在合格线以下仍按 4 档硬步进  
（`(9,7,5,3)`），0.1h 和 0.9h 同分，梯度全丢；② README / config 里写了「连续 3 天 <6 熔断」，  
但**代码里从未实现**（全仓 0 处命中）；③ 文档里的四维分是写入端 + 人读端双向可写，  
再跑一次 `ingest` 会把重算后的库值**覆盖回旧值**。

1. **分档细化（`score._band`）**：合格线以上维持 `5 / 7 / 9`；合格线以下按  
   `sub_floor`（默认 1）~ `sub_ceil`（默认 4）切整数带，`idx = int(value/ok * n)`；  
   用整数取带替代 `round()` 线性插值，规避浮点 + 银行家舍入的边界抖动。  
   阈值全部下沉到 `config.SCORE_THRESHOLDS` 的 `sub_floor` / `sub_ceil`，可逐维度调。
2. **熔断检测落地（`fuse.py`）**：绝对信号 = 连续 N 天（默认 3）低于阈值（默认 6）；  
   相对信号 = 近 7 日均值 vs 前 28 日均值，跌幅 ≥ `drift`（默认 1.0）→ 判「基线漂移」；  
   `long_run_days`（默认 14）标记「长期不达标」。CLI `fuse`（有绝对熔断时退出码 1），  
   `doctor` 新增 `[熔断检测]` 段（只提示、不影响 `is_healthy`）。
3. **分数单一权威（`sync_docs.py`）**：**库为准，文档由库渲染**。新增 CLI `sync-docs`  
   （`--check` 只测不写）回写两处：数据块分数行（追加在 `一句话总结` 后）+  
   「六、四维评分」表（4 列 `维度|分数|状态|待补字段`，`---` 分隔）；  
   语雀九段式导入件（`## 六` 标题含 `（1 – 10）`）跳过不动。  
   此后 `ingest` 读到的分数与库一致，**双向覆盖问题根除**。
4. **历史全量重算**：`.workbuddy/backup/recompute_scores_v140.py` 按新档重算 49 天四维 + 系统分，  
   **22 天变化**；7 月无字段支撑的人工分 **35 处一律置空**（口径：只用最新一套、格式统一）。
5. **一句话总结折叠**：`sync_summary_scores_v140.py` 把散文里的「健康 5」等旧分折到新分，  
   带时长单位负向断言（`0.5h` 不会被误吞成 `0`），15 处折叠、0 处时长污染。
6. **文档与模板同步**：`每日复盘模板.md` 六段表更新为 4 列 `无法评分` 口径；  
   `README` 重写评分章节（分档表 + 熔断规则 + 单一权威）。

**验证**：单测 201 → **225**（新增 `test_fuse.py` 8 项、`test_sync_docs.py` 11 项 + 分档 4 项），  
`ruff` 干净；`sync-docs --check` 幂等（0 篇待写）；重跑 `ingest` **0 处分数不一致**；  
`doctor` 数据健康。

**库内结果**：`daily_reviews` 49 行、`personal_tracks` 360 条、`integrity_check` ok 均未变（v4 schema）。

### v1.3.1 — 徒手训练计入运动时长

**背景**：三态口径修好了「未记录被误判」，但「做了徒手训练却没填分钟数」仍然  
落进「未记录」——而运动占健康分权重 0.25，是最重的子项。实测 W38 训练日  
运动达标长期为 **0/4**，指标实际失效。

1. 新增 `bodyweight.py` 折算模块 + `config.BODYWEIGHT_MOVES` / `BODYWEIGHT_RULES`：  
   「二、今日三件事」里提到俯卧撑即按确定性模型折算分钟数  
   （净执行时间 + 组间休息，单日 clamp 到 10–45min）。
2. 支持阿拉伯/中文数字、`A * B`（A=每组次数，B=组数）、`分 N 组` 等写法；  
   否定句（`没做`/`未做`/`忘了`）不折算。
3. **段落门控**：只扫「今日三件事」，不扫「AI 评价与建议」——后者会引用别的日期  
   （真实误判来源：9/20 评语提到「9/19 做过 100 个俯卧撑」）。
4. **字段优先、不叠加**：`运动时长_min` 已有数值时以字段为准，避免重复计数。
5. `daily_reviews` 新增 `exercise_src`（schema v3），已有数值回填 `record`；
