> 复盘仍是心脏，但要长出**采集、教练、督导、教师**四条四肢。

## 1. 定位与设计原则

### 1.1 三层分工（**保持不变**，新能力必须服从）

| 层 | 载体 | 职责 |
| --- | --- | --- |
| **执行层** | ClickUp | 我今天干了什么、有哪些待办（行为流水 / 习惯 / 书单 / 课表） |
| **源层** | 复盘 md（`每日复盘/复盘/YYYY-MM/`） | 人工可读的原文 + 机器可读的数据块 |
| **评价层** | `reviews.db` + `review_tool` | 评分 / 熔断 / 趋势 / 报告 |

### 1.2 五条设计原则（新增）

- **P1 · 截图是输入通道，不是数据源。** 体脂秤 / 薄荷健康 / 练练的截图只承担「人肉输入」，
  落盘形态一律是 **md 数据块 / 附录**，再由 `ingest` 入库。
  → 保住现有核心安全网：**库永远可从 md 100% 重建**（实测 49 天逐字段 0 差异）。
- **P2 · 不推翻既有四维与 72 天基线。** 新指标（体重 / 训练量 / 饮食合规）**不塞进四维**，
  另设独立指标区。理由：四维已进 CI 阻塞链（`recompute-scores` + `sync-docs --check`），
  改权重会让 72 天历史分与 7 份周报 / 2 份月报全部作废。
- **P3 · 零依赖 + 离线可测。** 截图解析由 AI 在对话里完成，**不引入 OCR / 图像库**；
  新增模块仍写 `unittest`，CI 保持阻塞。
- **P4 · 写盘后回读校验。** 本机写盘会间歇性「报成功不落盘」，所有写文件动作走 `safe-write` SOP。
- **P5 · 隐私数据不入 git。** 体重 / 体脂 / 饮食明细属敏感个人数据，只进 `reviews.db`
  （已 `.gitignore`），md 里的数值保持「只有当事人看得懂」的颗粒度即可。

## 3. 功能需求（FR）

> 统一句式：**触发 → 输入 → 处理 → 输出 → 数据落点 → 验收**。

### FR-A 生活记录官

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-A1 | 一条命令拿到当日 ClickUp 行为证据（**已实现** v1.6.0 `clickup` 子命令） | ✅ 已有 |
| FR-A2 | 对话口述 → 整理成结构化日流水（含时间锚点、类别） | P1 |
| FR-A3 | 「今日三件事」自动候选：从 ClickUp 完成项里按「有产出」排序取前 3，人工确认 | P1 |
| FR-A4 | 日流水按周聚合成「本周我做了什么」清单（区别于周报的分数视角） | P2 |

**FR-A2 细化**
- 处理：识别「做了 / 完成了 / 搞定了」类事件 → 拆成 `{时间, 类别(工作/学习/生活/健康), 事件, 产出}`。
- 落点：`每日复盘/复盘/YYYY-MM/YYYY-MM-DD.md` 的「二、今日三件事」（用户原文照录，AI 不改写）。
- 验收：连续 5 天从口述生成，用户只需修订不需要重写；`doctor` 对账保持干净。

### FR-B 体征官（身高体重 BMI）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-B1 | 建 `body_metrics` 表：体重 / 体脂率 / 腰围（日期为主键） | **P0** |
| FR-B2 | 身高作为**常量**进 `config.PROFILE["height_cm"]`，BMI 由库**派生**不入源 | **P0** |
| FR-B3 | 体脂秤截图 → 数值 → 回填复盘 md 数据块（`体重_kg` / `体脂率` / `腰围_cm`） | **P0** |
| FR-B4 | 趋势输出：体重 / BMI 折线 + 7 日均线 + 目标带（如 68–72kg） | P1 |
| FR-B5 | 目标管理：`goals` 表存目标值与期限，输出「按当前速率 X 周后到 70kg」 | P1 |
| FR-B6 | 异常预警：单周 ±1.5kg 以上 → 提示确认（同时联查训练量与热量，见 FR-G） | P2 |

**FR-B1 建议表结构（草案）**

```
body_metrics(
  date TEXT PRIMARY KEY,      -- 与 daily_reviews.date 同口径
  weight_kg REAL,             -- 体重
  body_fat_pct REAL,          -- 体脂率
  waist_cm REAL,              -- 腰围
  src TEXT,                   -- 'scale'=体脂秤截图 / 'manual'=手填
  note TEXT
)
```

**关键约束**：**BMI 不落库**（由 `height_cm` + `weight_kg` 派生渲染），
避免出现「库里的 BMI」与「按公式算的 BMI」两个权威 —— 沿用项目既有原则（派生值归库渲染，不入源）。

**FR-B3 验收**：截图 → md 数据块 → `ingest` → `doctor` 的字段完整度提升且对账干净；
**删库后能从 md 100% 重建**（P1 原则的硬性回归测试）。

### FR-C 运动教练

现状只有「运动时长分钟数」一个标量（含俯卧撑描述折算，`config.BODYWEIGHT_MOVES` 默认只启用俯卧撑）。
要成为教练，缺的是**结构**。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-C1 | 建 `training_sessions` / `training_items`：动作 / 组数 / 次数 / 时长 / 强度 | **P0** |
| FR-C2 | 练练 App 课表与完成截图 → 训练记录 + 与计划对账（练了 vs 排了） | **P0** |
| FR-C3 | `BODYWEIGHT_MOVES` 扩容：深蹲 / 卷腹 / 平板支撑 / 波比跳等（按现有结构追加） | P1 |
| FR-C4 | 训练计划表：按 `PROFILE["training_weekdays"]`（一三五二六）排出本周课表 | P1 |
| FR-C5 | 下周推荐：渐进超载（同动作组数 × 次数趋势）+ 部位轮换 + 恢复约束（连续训练天数上限） | P1 |
| FR-C6 | 训练量曲线：周总组数 / 总时长 / 分部位占比 | P2 |

**FR-C5 推荐引擎的最小规则（可解释、可复现）**
1. **达标线**：本周完成课次 ≥ 计划课次 × 0.8 才给「加量」建议，否则只给「先补次数」。
2. **渐进**：同一动作近 3 次的 (组数 × 次数) 均值稳定 → 建议 +1 组或 +2 次；波动大 → 维持。
3. **恢复**：连续训练 ≥ 3 天 → 强制插入 1 天恢复（与 `training_weekdays` 的周四 / 周日休息对齐）。
4. **部位轮换**：同一部位 48h 内不重复为主项。

**验收**：任一推荐都能说出「依据哪几天的哪几个数字」，且 CLI 可复算（不引入随机性）。

### FR-D 行为督导（日常行为清单）

现状：ClickUp「习惯与打卡」6 条习惯（每日阅读 30 分钟 / 练练健身 / 整理随手记 / 每日复盘总结 /
墨墨背单词 / 寻找好习惯）**只读、不落库**（sku `clickup-tracking` 边界②）。
→ 结果：习惯依从率**算不出来**，只能看素材。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-D1 | 建 `habit_logs` 表：`date + habit_key + done`，与 `personal_tracks` **物理隔离** | **P0** |
| FR-D2 | `habit_key` 归一化（复用 `core/tracks.py` 的思路，定义在 `config.HABITS`） | **P0** |
| FR-D3 | `clickup` 取数时可选 `--with-habits` 一并产出习惯完成情况 | P1 |
| FR-D4 | 依从率 / 连续天数进 `week` / `month` 报告（与补剂依从率**分表分栏**呈现） | P1 |
| FR-D5 | 断更预警：某习惯连续 N 天未勾 → 提示（N 可按习惯单独配置） | P2 |
| FR-D6 | 日常清单（ClickUp「日常事务」）→ 未完成项的滚动清单 + 逾期计数 | P2 |

🔴 **FR-D1 是一条需要用户拍板的边界变更**（见 §8 决策点 2）——
现规约写死「ClickUp 习惯不落库」。改法建议：**新表 + 新口径**，
`personal_tracks`（补剂 / 护肤）与 `habit_logs`（行为习惯）**永不合并**，
`doctor` 新增一条对账守卫「两表 key 不得交叉」，把边界从「口头约定」升级为「代码强制」。

### FR-E 营养师（饮食管理及推荐）

现状：`diet_kcal` + `carbs_g` / `fat_g` / `protein_g` 四个日汇总字段，
目标基线在 `PROFILE["macro_targets"]`（碳水 220g / 蛋白 82g / 脂肪 46g）。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-E1 | 薄荷健康截图 → 热量 + 三大营养素 + 三餐完成情况，回填数据块 | **P0** |
| FR-E2 | 缺口分析：当日 / 近 7 日均值 vs `macro_targets`，指出**缺在哪一餐** | **P0** |
| FR-E3 | 「常吃食物库」（`config.FOOD_LIB`，20–30 项，含宏量）→ 把缺口翻译成**具体动作** | P1 |
| FR-E4 | 三餐结构评分：早餐按时 / 加餐次数 / 晚间热量占比 | P2 |
| FR-E5 | 食物级明细（`nutrition_items` 表，一天 10+ 行） | P3（可选） |
| FR-E6 | 极端值拦截：连续 3 天热量 < 1000kcal → 强提示（不作为「做得好」） | P2 |

**FR-E3 示例（这是「推荐」的可落地形态）**
> 缺口：蛋白质 82 − 55 = **27g**
> 建议：晚餐加 1 份鸡胸（200g ≈ 46g 蛋白）或 2 个鸡蛋 + 250ml 牛奶（≈ 26g）
> —— 全部数字来自 `FOOD_LIB`，不是模型编的。

🔴 需要用户拍板：饮食颗粒度做到**日汇总**（FR-E1/E2，成本低）还是**食物明细**（FR-E5，成本高）？见 §8。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |

### FR-G 总管家（编排层）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-G1 | **晨间 brief**：昨日分数 + 熔断 + 今日训练计划 + 饮食目标 + 待办 Top 3 | P1 |
| FR-G2 | **夜间复盘**：整合六路素材（ClickUp / 体征 / 训练 / 饮食 / 学习 / 对话）出成品复盘 | P1 |
| FR-G3 | **跨维关联**：睡眠 ↔ 训练量 ↔ 体重 ↔ 热量 ↔ 学习投入的联合观察 | P2 |
| FR-G4 | **周度管家报告**：四维 + 体征 + 训练 + 饮食 + 习惯 + 学习 六段合一 | P2 |
| FR-G5 | 熔断升级：任一独立指标（体重偏离 / 习惯断更 / 训练连续缺席）触发时纳入统一告警 | P2 |

**FR-G3 示例（跨维关联的价值，纯相关性陈述，不下因果结论）**
> 近 14 天：睡眠 < 6.5h 的 5 天里，有 4 天训练时长为 0；睡眠 ≥ 7h 的 6 天里，5 天完成训练。
> → 提示：把训练安排在睡眠较好的日子，而不是硬扛。

⚠️ **FR-G3 的统计纪律**：样本 < 10 组时只输出「观察」，不输出「结论」；
所有相关系数必须由脚本算（不手写），与周报的极值断言同一套纪律。

## 4. 数据需求

### 4.1 新增表（4 张）

| 表 | 用途 | 主键 | 与既有表的关系 |
| --- | --- | --- | --- |
| `body_metrics` | 体征 | `date` | 独立，**无外键**（允许只称重不写复盘） |
| `training_sessions` | 训练课 | `date + session_key` | 明细合计派生 `exercise_min`（仅空值时） |
| `training_items` | 训练动作明细 | `date + session_key + item_key` | 隶属 session |
| `habit_logs` | 行为习惯 | `date + habit_key` | ⛔ **与 `personal_tracks` 物理隔离** |
| `learning_logs` | 学习记录 | `date + topic_key` | 与 `learn_h` 互为证据与汇总 |
| `review_queue` | 复习队列 | `topic_key` | **可选**；必须可从 `learning_logs` 重建 |

> **五张表 + 一张可选**。训练拆两级（session / item）——**别合并**：课是「计划单位」，动作是「推荐单位」。
>
> 📌 **相对本文初稿的修正**：原 `goals` 表**已取消** —— 目标值（体重目标 / 周训练次数）
> 属**配置**而非数据，改为写 `config.PROFILE`。理由：目标是单值、不需要历史；进表会让它成为
> 唯一一份**无法从 md 重建**的状态，直接破坏 §4.5 的底线。
> 结构细节（DDL 草案 / md 格式 / 迁移版本）见 [`生活管家路线图.md`](生活管家路线图.md)。

### 4.2 md 侧新增（**源在这里**）

复盘 md 的 ```` ```data ```` 块新增字段（顺序追加在末尾，保持现有字段顺序不变）：

体重_kg:
体脂率:

| 体脂秤 | 截图 | AI 读图 → md | 每周 1–3 次 |
| 薄荷健康 | 截图 | AI 读图 → md | 每日 |
| 练练 App | 截图 | AI 读图 → md | 每次训练 |
| 对话口述 | 对话 | 现场整理 | 随时 |

### 4.4 权威归属（沿用 §1.2 原则 + 新增）

| 对象 | 权威 | 收敛方式 |
| --- | --- | --- |
| 体征 / 训练 / 学习 / 饮食明细 | **md（源）** | `ingest` |
| BMI 等派生值 | **库** | 渲染时算，不入源 |
| 习惯勾选状态 | **ClickUp**（执行层） | 快照落 `habit_logs`，只读不回写 |
| 四维分 / 系统分 | **库**（不变） | `recompute-scores --apply && sync-docs` |

### 4.5 可重建性（**这是本方案的底线，务必守住**）

> 「删库 → 只用 md 从零重建 → 逐字段比对 0 差异」是现有系统的核心质量保障（CI 阻塞项）。
> **新增数据的通道设计必须让它继续成立** —— 否则截图数据一旦丢失就永久丢失。

验收硬指标：新增 6 张表全部纳入 CI 重建比对；`doctor` 新增对账项覆盖新表。

## 6. 边界与不做项（**明确排除**）

- ⛔ **不重构四维评分**、不改权重、不动 72 天历史分（避免周报 / 月报集体作废）。
- ⛔ **不合并** `personal_tracks` 与 `habit_logs`（补剂 / 护肤 vs 行为习惯）。
- ⛔ **不引入新的定时任务**（本项目无调度；一切按需触发，由用户投递素材）。
- ⛔ **不打开 `new-day`**（`FEATURES["new_day"] = False` 是刻意为之）。
- ⛔ **不做医疗 / 营养处方**：只做「趋势 + 缺口 + 可执行动作」，不做诊断，异常一律转人工。
- ⛔ **不为推送 / 代理造缓解方案**（沿用既有决定）。
