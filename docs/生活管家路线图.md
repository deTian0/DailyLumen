## 2. 全局口径（**七个里程碑都适用，先读这一节**）

### 2.1 ✅ 已定稿的五条（直接照做，别再问）

| # | 口径 | 理由 |
| --- | --- | --- |
| **G1** | **截图是输入通道，不是数据源。** 一切新数据先落 **md**（数据块 / 附录章节），再由 `ingest` 入库 | 保住核心安全网：删库可从 md 100% 重建（实测逐字段 0 差异） |
| **G2** | **不重构四维评分、不改权重、不动 72 天历史分。** 新指标另设独立区 | 四维在 CI 阻塞链上（`recompute-scores` + `sync-docs --check`），改权重会让 7 份周报 + 2 份月报集体作废 |
| **G3** | **派生值不入源。** BMI、7 日均线、依从率等一律由库 / 报告渲染时算 | 沿用既有原则（分数归库渲染，md 里手改是白改） |
| **G4** | **目标值是配置不是数据。** 体重目标、周训练次数等写 `config.PROFILE`，**不进表** | 目标是配置、单值、不需要历史；进表会破坏可重建性 |
| **G5** | **新表不参与四维评分。** 体征 / 训练 / 习惯 / 学习全部是**独立指标区** | 与 G2 同源；`doctor` 的 `is_healthy` 判定口径保持唯一 |

### 2.2 三条新增红线（违反即返工）

- 🔴 **R1 · 不许出现「口径两套」。** 任何指标（热量缺口、训练达标、习惯依从率）只能有一个算法来源。
  已有实现的（如 `reports/ai_review.py` 的饮食关注点、`reports/analyze.py` 的依从率），
  新报告**必须复用**，不许另写一份。
- 🔴 **R2 · `exercise_min` 仍是健康分的唯一运动输入。** 训练明细是它的**证据来源**，不是替代品。
  「明细合计 → `exercise_min`」只在**字段为空**时生效（字段优先、不叠加），且 `exercise_src='derived'`。
- 🔴 **R3 · `habit_logs` 与 `personal_tracks` 永不合并。** 前者是行为习惯（ClickUp 执行层），
  后者是补剂 / 护肤（复盘 md 源）。`doctor` 加**代码守卫**：两表 key 不得交叉。

### 2.3 每次新增表都要做的三件事

1. `schema.sql` 加 `CREATE TABLE IF NOT EXISTS`（含 CHECK 约束）
2. `storage/db.py` 的增量迁移推进 `PRAGMA user_version`；`_create_indexes` 补索引
3. **重建 `reviews.example.db`**（`tests/test_example_db.py` 守卫同版，否则新用户首次 ingest 被 CHECK 拒绝）

## 3. 里程碑详情

### M9 — 体征基线（体重 / BMI / 体脂 / 腰围）｜P0｜v1.13.0

**目标**：把「体重管理」从零建起来 —— 截图 → md → 库 → 趋势，并守住可重建性。

**为什么排第一**：体重是所有推荐引擎（训练强度、热量缺口）的**共同输入**，缺它后面全是猜。

**范围（文件级）**

| 动作 | 文件 |
| --- | --- |
| 新增表 | `review_tool/schema.sql`（`body_metrics`） |
| 迁移 | `review_tool/storage/db.py`：`user_version` 4 → 5；`upsert_body_metrics` / `load_body_metrics`；索引 `idx_body_date` |
| **新增模块** | `review_tool/core/body.py`（**core 层，零 I/O，禁 `import sqlite3`**） |
| 配置 | `review_tool/config.py`：`PROFILE["height_cm"]`；`BODY_TARGETS`；体征字段登记 |
| 解析 | `review_tool/pipeline/parse.py`：识别 `体重_kg` / `体脂率` / `腰围_cm` |
| 入库 | `review_tool/pipeline/ingest.py`：体征字段 → `body_metrics`（**不写 `daily_reviews`**） |
| 报告 | `review_tool/reports/body.py`（新）；`reports/doctor.py` 加 `[体征]` 段 |
| CLI | `review_tool/__main__.py` 的 `ROUTES` 加 `body` |
| 测试 | `tests/test_body.py`（新）、`tests/test_body_ingest.py`（新）、`tests/test_migration_v5.py`（新） |
| 模板 | `每日复盘模板.md`：数据块加三行 |
| 文档 | `README.md`（CLI 表 + 模块地图 + 测试数）、`review_tool/README.md`、`docs/设计说明.md`（字段速查 + 变更日志） |
| skill | `.workbuddy/skills/daily-review-intake/SKILL.md` 加「§3.5 体征截图回填规则」 |

**DDL 草案**

```sql
CREATE TABLE IF NOT EXISTS body_metrics (
    date         TEXT PRIMARY KEY,              -- 与 daily_reviews.date 同口径
    weight_kg    REAL
        CHECK (weight_kg IS NULL OR (weight_kg > 0 AND weight_kg < 400)),
    body_fat_pct REAL
        CHECK (body_fat_pct IS NULL OR (body_fat_pct BETWEEN 0 AND 70)),
    waist_cm     REAL
        CHECK (waist_cm IS NULL OR (waist_cm > 0 AND waist_cm < 300)),
    src          TEXT
        CHECK (src IS NULL OR src IN ('scale', 'manual')),  -- 体脂秤截图 / 手填
    note         TEXT
);
```

**md 侧（源在这里）** —— 数据块末尾追加三行，保持既有字段顺序不动：

```
体重_kg:
体脂率:
腰围_cm:
```

**核心口径**

- ✅ **BMI 不入源、不进库**（G3）：由 `height_cm`（config）+ `weight_kg`（库）在渲染时算。
- ✅ **`daily_reviews` 不加这三列**：一表一责，避免两份权威。
- ✅ **`height_cm` 留空时不报错**：BMI 显示「未配置身高」；M9 **不阻塞**于用户提供数值。
- ✅ **同一天重复 ingest 走 upsert**：默认保护模式（只补空），与 `daily_reviews` 一致。
- 📌 `body_metrics` **不设**对 `daily_reviews` 的外键：允许「只称了体重、没写复盘」的日子独立存在。

**`core/body.py` 职责（纯函数，可离线测）**

| 函数 | 输出 |
| --- | --- |
| `bmi(weight_kg, height_cm)` | BMI 保留 1 位；身高为空返回 `None` |
| `bmi_band(bmi)` | `偏瘦 / 正常 / 超重 / 肥胖`（按中国标准：18.5 / 24 / 28） |
| `moving_average(series, window=7)` | 7 日均线（窗口内缺失日不参与分母） |
| `weekly_delta(series)` | 最近 7 日 vs 前 7 日均值差 |
| `distance_to_target(weight, low, high)` | 距目标带（带内返回 0） |
| `eta_weeks(current, target, weekly_delta)` | 按当前速率外推周数；速率符号不符返回 `None` |

**新增 CLI**

```bash
python -m review_tool body              # 最新值 + BMI + 7 日均 + 周变化 + 距目标
python -m review_tool body --json       # 结构化输出
```

- [x] **重建回归**：删库 → 只用 md 从零重建 → `body_metrics` **逐字段 0 差异**
- [x] `doctor` 新增 `[体征]` 段（最新体征距今 / 体重单周突变 > 1.5kg 提示），**建议性、不影响 `is_healthy`**

### M10 — 训练结构化（课 / 动作明细 + 推荐）｜P0｜v1.14.0

**目标**：把「运动时长一个标量」升级成「课 → 动作 → 组次」的结构，并给出**可解释**的下周推荐。

**背景**：现有 `exercise_min` 只有总量；`BODYWEIGHT_MOVES` 只折算描述里的徒手动作（默认仅俯卧撑），
且训练日没填按 0 计（v1.3.2 口径）。教练角色缺的是**结构**与**计划**。

**范围（文件级）**

| 动作 | 文件 |
| --- | --- |
| 新增表 | `schema.sql`：`training_sessions` + `training_items` |
| 迁移 | `storage/db.py`：v5 → **v6**；`upsert_training` / `load_training` |
| **新增模块** | `core/training.py`（明细行解析 + 合计 + 推荐规则） |
| 配置 | `config.py`：`TRAINING_MOVES`（动作目录）、`TRAINING_PLAN`（可选课表）、`COACH_RULES`；`BODYWEIGHT_MOVES` **扩容**（深蹲 / 卷腹 / 平板支撑 / 波比跳） |
| 解析 | `pipeline/parse.py`：解析「附录 · 训练明细」章节 |
| 入库 | `pipeline/ingest.py`：明细 → 两表；**明细合计派生 `exercise_min`** |
| 报告 | `reports/coach.py`（新）；`reports/analyze.py` 周报加「训练结构」段 |
| CLI | `ROUTES` 加 `coach` |
| 测试 | `tests/test_training.py`、`tests/test_coach.py`、`tests/test_migration_v6.py` |
| 文档 | 同上四处 + `docs/设计说明.md` 记「明细 vs 标量」口径 |

**DDL 草案**

```sql
CREATE TABLE IF NOT EXISTS training_sessions (
    date        TEXT NOT NULL,
    session_key TEXT NOT NULL,        -- 'main' / 'morning' / 'evening'
    plan_name   TEXT,                 -- 课表名（如 'A-胸背'）
    src         TEXT
        CHECK (src IS NULL OR src IN ('lianlian', 'self')),
    total_min   INTEGER
        CHECK (total_min IS NULL OR total_min >= 0),
    note        TEXT,
    PRIMARY KEY (date, session_key)
);

CREATE TABLE IF NOT EXISTS training_items (
    date        TEXT NOT NULL,
    session_key TEXT NOT NULL,
    item_key    TEXT NOT NULL,        -- 归一化动作 key（在 config.TRAINING_MOVES 里）
    item        TEXT NOT NULL,        -- 展示名
    sets        INTEGER,
    reps        INTEGER,
    minutes     REAL,
    load_kg     REAL,
    PRIMARY KEY (date, session_key, item_key)
);
```

**md 侧（源在这里）** —— 复盘 md 新增一节「附录 · 训练明细」：

```
## 附录 · 训练明细

- 计划：A-胸背｜来源：练练
- 俯卧撑 4×20
- 卧推 3×12 @40kg
- 平板支撑 3×60s
- 跑步 20min
```

**解析规则（`core/training.py`，确定性、无随机）**

| 行格式 | 解析结果 |
| --- | --- |
| `名称 组×次` | `sets` / `reps` |
| `名称 组×次 @负重` | 追加 `load_kg` |
| `名称 Nmin` / `名称 N分钟` | `minutes` |
| `名称 组×时长s`（如 `3×60s`） | `sets` + 折算 `minutes` |
| 首行 `- 计划：X｜来源：Y` | session 元信息 |

**推荐规则（`reports/coach.py`，可解释、可复算）**

1. **达标线**：本周完成课次 ≥ 计划课次 × `COACH_RULES["min_ratio"]`(0.8) 才给「加量」，否则只给「先补次数」。
2. **渐进**：同一动作近 3 次的 (组×次) 均值**稳定**（波动 ≤ 10%）→ 建议 +1 组或 +2 次；波动大 → 维持。
3. **恢复**：连续训练 ≥ `max_consecutive_days`(3) → 强制建议插入 1 天恢复，与 `training_weekdays`（一三五二六）对齐。
4. **部位轮换**：同一 `body_part` 48h 内不重复作主项。
5. **输出纪律**：每条建议必须打印**依据的数字**（哪几天、哪几个值）。

**核心口径**

- 🔴 **R2 落地**：明细合计只在 `exercise_min` 为空时派生，标 `exercise_src='derived'`；
  ⛔ **不加新的 `exercise_src` 枚举值**（那要重建表改 CHECK）——语义相同，复用 `derived`。
- ✅ **`TRAINING_MOVES` 与 `BODYWEIGHT_MOVES` 分离**：前者是动作目录，后者是徒手折算参数；
  `BODYWEIGHT_MOVES` 的每个 key **必须**在 `TRAINING_MOVES` 里存在（加测试守卫），
  两者 alias **不得互相抢匹配**（并入 `tests/test_config.py` 的既有校验）。
- ✅ **训练明细仍不参与四维**（G5）：它只影响 `exercise_min` 这个既有输入，路径不变。

**验收清单**

- [x] schema 推到 **v6**；`reviews.example.db` 同版
- [x] 明细解析覆盖上表五种行格式，各一例单测
- [x] 🔴 **回归**：引入训练明细后，**全库四维分与字段重算完全一致**（`doctor [分数一致性]` ✓）
- [x] `exercise_min` 派生路径单测：字段为空 → 派生 `derived`；字段有值 → **不叠加**、`src` 保持 `record`
- [x] `coach` 的每条建议都能打印依据；同输入两次运行输出**逐字节一致**（无随机）
- [x] **重建回归**：两表逐字段 0 差异
- [x] 文档 / skill 同步；版本 **v1.14.0**；commit + tag

**🔴 决策点**：练练 App 的截图能拿到多少信息（课名？动作？组次？）——
